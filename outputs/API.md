# Контракт мока

Все методы возвращают Promise. Запросы выполняются около 350 мс. Копии данных отделены от внутреннего хранилища: локальное изменение объекта не меняет сервер.

| Метод                                    | Результат                      |
| ---------------------------------------- | ------------------------------ |
| `api.list(filters, cursor?, signal?)`    | `{ items, nextCursor, total }` |
| `api.get(id, signal?)`                   | Заявка                         |
| `api.update(id, { status, assigneeId })` | Обновлённая заявка             |
| `api.failNextRequest()`                  | Следующий запрос вернёт 503    |
| `api.reset()`                            | Сброс данных и ошибки          |

Заявка: `{ id, title, customer, status, assigneeId }`. Все ID — строки. Статусы: `new`, `active`, `closed`. Сотрудники экспортируются как `employees`.

Фильтры: `{ q: string, status: Status | '', assigneeId: string }`. Пустые строки означают отсутствие ограничения. Поиск без учёта регистра по теме и клиенту; пробелы по краям игнорируются. Условия соединяются через «и».

Размер страницы — 12 записей. Первая страница запрашивается с `cursor = null`. Для следующих используйте `nextCursor` ответа, не вычисляйте его самостоятельно. Курсор действителен для конкретной выборки. Порядок стабилен по исходной позиции; мутация его не меняет. `total` — размер всей отфильтрованной выборки.

`ApiError` содержит `status`, `message` и `fieldErrors`. Для 422 ключи ошибок — `status` и/или `assigneeId`. Максим (`max`) не может принимать закрытые заявки: это предсказуемый пример бизнес-ошибки. Пустые и неизвестные значения также отклоняются. Неудачная мутация не меняет данные. 404 — запись не найдена, 503 — искусственная общая ошибка.

`AbortSignal` поддерживается для чтения: отменённый запрос не возвращает данные. Мок всё равно дожидается задержки; это не ограничение на способ обработки гонок в приложении.

Данные живут в памяти модуля. Перезагрузка сбрасывает записи; копирование ссылки в другую вкладку проверяет восстановление фильтров на исходном наборе. Многопользовательские конфликты и авторизация вне задания.

## RTK Query

UI использует хуки из `entities/ticket`, а не вызывает мок напрямую. Готовы запросы `getTickets({ filters, cursor })`, `getTicket(id)` и мутация `updateTicket({ id, patch })`. `queryFn` адаптирует методы мока и передаёт AbortSignal для чтения.

Ошибка RTKQ сериализуется как `{ status, message, fieldErrors }`. При использовании `.unwrap()` проверяйте поля объекта: `instanceof ApiError` относится к низкоуровневому моку и здесь не работает. Инвалидация и ручное обновление кеша после мутации оставлены как часть задания.
